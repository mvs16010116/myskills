## 平台心智模型（所有主题共用）

**四级链路**——U9 的每个业务动作都走这条链：

```
界面  →  服务  →  实体  →  数据库
(UI)     (BP/SV)   (BE)     (物理表)
```

**元数据驱动**——这是 U9 与普通 Web 应用最本质的区别：

- 实体（BE）**不只是表结构**，还含校验规则、默认值、组织/币种维度、索引。这些定义存在**元数据库（Metabase）**，不在业务数据库
- 界面字段 ≠ 物理字段：可能是物理字段、公式计算字段（`计算列`）、跨组织引用字段、扩展字段
- 二开的核心动作是**「改元数据、写服务、配界面」三元组**，不是改数据库
- 物理表由框架**从元数据自动生成**（生成代码 / 发布 DSL 到元数据库 / 执行建库脚本三条线并行）

**两类数据库**：业务数据库（业务数据 + 物理表）、元数据库（实体定义、属性定义、校验规则、UI 元数据）。**二开设计的权威源是元数据库。**

**服务可见**——实体属性的 `服务可见 = True/False` 决定该字段是否出现在对外服务与 DTO 中。这是 DTO 字段清单的源头，也是 DTO 清单**无法覆盖全量字段**的根本原因。

## 硬护栏

1. **绝不直接连 SQL Server 改表加字段**。手改列后 UBF 感知不到、元数据发布会报错、升级会被标准元数据覆盖。扩展字段走弹性域或扩展实体（见 ③）
2. **物理表前缀不可凭记忆断言**。公网上 `CBO_`/`SM_`/`PM_`/`InvTrans_` 与 `T_BAS_`/`T_SO_` 两套说法互相矛盾且均未经权威验证。**获取物理表名的唯一可靠途径是查 U9 元数据库**，或走 BE 实体查询 + F12 反查（见 ②）
3. **扩展字段要进审批流/下游，必须设 `TransferFlag`（允许传递）**，否则下游永远读不到该字段值
4. **U9C 报表必须有查询条件**，否则打开后不显示任何数据——这是设计如此，不是 bug
5. **环境类问题优先用 Everything 搜缺失文件**。U9C/UBF 的"稀奇古怪问题"绝大多数是安装时文件不完整导致
6. **公网 U9 客开资料有大量 AI 生成的假 API**。判据是**命名空间**：真实代码只用 `UFSoft.UBF.*` 或 `UFIDA.U9.*`；出现 `U9.Platform` / `U9.BO` / `U9.Common` / `BEAS` 的一律丢弃。详见 `references/sources.md` 第 6 章
