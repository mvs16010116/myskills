## 1. 平台总览

### 1.1 UAP 与 UBF 的关系

`【官方】`

- **UAP**（Unified Application Platform，统一应用平台）是用友 U9 cloud 的**客户化开发平台**。不是独立产品，而是"开发 + 集成 + 运行 + 管理"的解决方案平台
- **UAP Studio IDE** 是 UAP 的开发工具集，提供实体设计器、表单设计器、报表设计器、打印模板设计器、流程设计器等
- **UBF**（UAP Business Framework）是 UAP 的**底层业务框架**。集成在 Visual Studio 里的开发插件历史上称 **UBF Studio**，新版称 **UAP Studio**，**两者指同一套工具**
- 关键定位：**UAP 提供的开发工具就是原厂开发 U9 所用的同一套工具**。客开产物与原厂功能的应用模式完全一致，可实现"无痕迹个性化"

### 1.2 运行时架构

`【社区】`

```
浏览器 / 客户端
      ↓
IIS 承载的 Web 服务层
      ↓  WCF 调用
应用服务器上的业务服务
      ↓
SQL Server 数据库
```

业务动作经过**四级链路**：

```
界面  →  服务  →  实体  →  数据库
(UI)     (BP/SV)   (BE)     (物理表)
```

### 1.3 元数据驱动机制（理解 U9 二开的钥匙）

`【社区】` `【官方】`

这是 U9 与普通 Web 应用最本质的区别：

- **实体（BE）不只是数据库表结构**。它还包含**字段校验规则、默认值、组织和币种维度定义**等。这些定义**全部存放在元数据库（Metabase）中**，而非业务数据库
- **界面字段不一定对应物理字段**。你在 U9 界面上看到的字段，可能是：
  - 物理字段
  - 公式计算字段
  - 跨组织引用字段
  - 扩展字段
- **客户化开发的核心动作是「改元数据、写服务、配界面」三元组**，而不是"改数据库"

> **这是全篇最重要的一句话**：U9 二次开发改的是**元数据**，物理表由框架从元数据自动生成。任何绕过元数据直接改物理表的做法都会在升级时崩掉。

### 1.4 两类数据库

| 数据库 | 存放内容 | 说明 |
|---|---|---|
| **业务数据库** | 实际业务数据 + 物理表结构 | 标准表 + 扩展表 |
| **元数据库（Metabase）** | 实体定义、属性定义、校验规则、默认值、组织/币种维度、UI 元数据 | **二开设计的权威源** |

`【社区】` 提到的物理表分类（**`【待核实】`**）：

- 标准业务表：以 `T_BAS_`、`T_SO_` 等前缀开头
- 扩展表：默认带 `_EXT` 后缀，或按扩展包命名

> ⚠️ **表前缀存疑警告**
>
> 公网上关于 U9 物理表前缀的说法**互相矛盾**：有说 `CBO_` / `SM_` / `PM_` / `InvTrans_` 的（与 UBF 实体命名空间对应），也有说 `T_BAS_` / `T_SO_` 的。**两套说法均未经权威验证**，且部分来源标注为 AI 生成。
>
> **在拿到元数据库或官方数据字典之前，不要把任何一套表前缀当作事实。** 获取物理表名的唯一可靠途径是查询 U9 元数据库，或走 BE 实体查询 + F12 反查（见 `references/api-dto.md`）。

### 1.5 关键概念词汇表

`【手册】` UBFStudio 使用手册 V2.8 原文

| 中文 | 英文 | 解释 |
|---|---|---|
| 元模型 | Meta-Model | 描述系统模型的模型。对业务系统抽象建模产生系统模型，对系统模型再抽象建模就产生元模型 |
| 元数据 | Meta-Data | 描述元模型的数据 |
| 领域模型 | Domain Model | 用来构建特定领域软件系统的知识模型，是合并了数据和行为的对象模型 |
| 业务实体 | Business Entity | 领域模型中的业务数据对象，如订单头、订单体、职员、客户 |
| 业务操作 | Business Process | 领域模型中的业务逻辑对象，描述对象行为，如订单增加、修改、删除 |
| 服务 | Service | 领域模型中对外公开操作的业务逻辑对象，是系统互连和流程配置的接口 |
| 数据传输对象 | Transient Object（DTO） | 普通类，**不参与持久化**，主要用作 BP 的参数和返回类型（不能在持久化对象中使用） |
| 属性类型 | Property Type | 不能单独持久化、没有 ID 的小对象，常用于货币、日期范围等描述（原名"值对象"） |
| 枚举类型 | EnumType | 被命名的整型常数的集合，如销售类型、付款方式、运输方式 |
| 校验器 | Validator | 生成对属性等校验的框架代码，可作为公用 |
| 模式 | Pattern | 可重用的、可自定义的领域模型模式。多个实体、属性类型、枚举及其关系的组合 |
| 特性 | Feature | 被抽象出来并可在实体设计时被复用的、代表特定方面（Aspect）特征的属性集 |
| 应用字典 | Application Dictionary | 特定的属性规范，用于类属性的重用 |
| 版型 | Stereotype | 扩展业务实体描述的一种解决方法；主要用于表现一些不在模型上体现的业务规则，**主要用于扩展代码** |
| 模型图 | Model Diagram | UBF 文档的图形化显示方式，可直接在模型图中编辑 |
| 类图 | Entity Diagram | 领域模型的图形描述，可包含多个类并表明类间关系 |
| 数据库图 | Database Diagram | **不描述真正的数据库**，只是表和表关联的图形描述 |

### 1.6 核心红线

`【社区】`

> **绝对不要直接连 SQL Server 改表加字段。**

原因：

1. U9 的表结构与元数据强绑定。手动加列后 **UBF 完全感知不到**
2. 后续**元数据发布会报错**
3. **升级时会被标准元数据整体覆盖**，或标准功能运行时读不到该列直接页面报错
4. 回退成本远高于走平台扩展

**正规做法**：走扩展字段机制（见 [第 6 章](#6-扩展字段客开的核心场景)）。

## 2. IDE 与工具族

### 2.1 集成开发环境组成

`【手册】`

UBF Studio 是**基于模型驱动的可视化开发工具**，界面风格仿 MS Visual Studio.NET。

- **文档编辑区域**：中间主体，显示被编辑文档的模型图。UBF Studio 中的开发工作**主要通过图形化方式进行**
- **工具窗体**：分布在左右两侧和底部
  - **公共管理工具**（右侧）：解决方案管理器、模型管理器、属性页、发布对象浏览器（四个页签）
  - **输出查看器**（底部）
  - **针对特定文档的操作工具**（左侧）

### 2.2 公共管理工具

`【手册】`

**解决方案管理器**

- 解决方案是 UBF Studio 操作的**主文件**，代表一个完整的业务模型
- 结构：一个解决方案由多个项目组成 → 一个项目可包含多个文档 → 一个文档对应 Windows 文件系统中的一个文件
- 除 `Reference` 节点外，各节点都代表真实的 Windows 文件或文件夹
- 解决方案文件扩展名：`.ubfsln`

**模型管理器**

- 设计期的模型通过模型管理器浏览和统一管理
- 模型通过**项目**进行分组，不同种类有不同的图标

**发布对象浏览器**

- 浏览**运行期**的模型
- 已发布的模型组件在 Windows 文件系统中标记为 `MetaData.dll` 扩展名
- 无效的组件链接图标显示不同
- ⚠️ **运行态的组件无法显示其属性**——属性页对发布对象浏览器中显示的组件及其下级元素不做显示

**输出查看器**

- 动态显示当前程序运行的日志信息：错误、警告、提示、调试信息
- 通过顶部工具栏按钮切换查看不同类型信息

### 2.3 九大设计器

`【手册】`（手册称"9 个主要开发工具"，实际列举 9 项 + 应用组装工具）

| 设计器 | 用途 |
|---|---|
| **实体模型设计器** | 构建企业数据模型，设计业务实体及实体间关系。可发布实体模型并产生实体模型的代码 |
| **状态机设计器** | 设计指定实体的状态机。可生成状态机框架代码，开发人员在框架内填写状态变迁规则 |
| **服务设计器** | 规划业务处理规则和服务，定义接口，**指定数据库事务模式**。生成业务处理或服务的框架代码 |
| **UIModel 设计器** | 设计用于界面显示的数据模型，同时设计界面数据的处理行为 |
| **Form 设计器** | 设计与用户交互的页面。进行布局规划、交互行为设计、**控件与 UIModel 的界面数据模型绑定** |
| **参照设计器** | 设计参照页面。参照页面属于 Form 设计的一个**独特分支**，通常具有相似布局和交互行为，故提供专门设计器 |
| **报表设计器** | 设计报表的**布局和数据源** |
| **打印设计器** | 设计打印的**内容和样式**，成为打印模板 |
| **查询设计器** | 设计查询方案。主要包括设计栏目及栏目显示顺序、设计查询条件 |
| 应用组装工具 | 组装应用层级树 |

### 2.4 项目类型与文件扩展名

`【手册】`

| 项目类型 | 文件扩展名 | 说明 |
|---|---|---|
| 实体项目 | `.ubfmlproj` | 实体组件文件扩展名 `.ubfbe` |
| 操作项目 | `.ubfbpproj` | 操作组件文件扩展名 `.ubfbp` |
| 服务项目 | `.ubfserproj` | — |
| 数据库项目 | `.ubfdbproj` | 由实体项目创建 |
| 特性项目 | `.ubffeproj` | 用于模型复用 |

`【社区】` 补充的简称对应：**BE** = 实体项目，**BF** = 操作项目，**SV** = 服务项目；另有**分析项目**（打印模板）、**报表应用项目**（报表）。

### 2.5 项目内部结构

`【手册】`

1. 每个项目包含一个**项目文件**和一个**同名文件夹**
2. 文件夹下包含若干**组件文件**，每个文件代表一个组件
3. 组件中包含**命名空间、模型、模型图**，组件内部结构通过模型管理器显示和管理
4. 模型和模型图通过**图形化编辑器**打开并修改

### 2.6 源代码版本管理

`【手册】`

UBF Studio 支持与版本管理工具集成，支持大规模团队开发：

- 支持的工具有 **MS Visual SourceSafe V6.0**（或更高）、**IBM Rational ClearCase 2003 及以下**
- 可在两种工具之间切换

**加入版本管理**：

1. 先将解决方案的**整体文件夹**放到版本管理工具的控制文件夹中
2. 运行 UBF Studio，打开解决方案
3. 主菜单 → 文件 → 源代码管理 → 绑定
4. 单击任意一项的"改变"按钮，在不绑定 / VSS 绑定 / ClearCase 绑定之间选择，下一步

**断开**：主菜单 → 文件 → 源代码管理 → 断开

**文件状态图标**：

| 图标含义 |
|---|
| 该文件还没有加入到源代码管理服务中 |
| 该文件处于未签出状态 |
| 该文件处于签出状态 |
| 该文件正被他人签出 |

**版本管理操作**（文档上下文菜单）：签出、签入、撤销签出、取得最新版本、加入到源代码管理服务。

### 2.7 模型图操作技巧

`【手册】`

**工具箱创建模型**：模型工具箱提供针对当前模型的特定工具，一般通过**拖曳**方式加入模型图。

> **小技巧**：在模型图的**空白处双击**，可快速创建当前模型图中最常用的模型：
> - 实体类图 → 快速创建**实体**（适用于实体项目、模式项目、特性项目）
> - 操作类图 → 快速创建**操作**（适用于操作项目）
> - 服务类型 → 快速创建**服务**（适用于服务项目）
> - 数据库图 → 快速创建**数据表**（适用于数据库项目）

**模型选择**：

- 点击模型标题 → 选择单个模型
- 拖曳画矩形框 → 同时选择多个模型
- 背景右键 → 全选（快捷键 `Ctrl+A`）

**模型快速复制**：选中模型 → 右键"复制" → 右键单击模型图背景 → "粘贴"

**模型删除**（⚠️ 两者区别重大）：

| 操作 | 快捷键 | 效果 |
|---|---|---|
| 右键"删除" | `Del` | 模型从模型图中消失，但**在当前组件中仍然存在**，模型管理器中仍可见 |
| 右键"**从元数据删除**" | `Shift+Del` | 模型从模型图和组件中**都被删除**。**危险操作，删除后模型无法恢复** |

**模型图显示控制**（背景右键菜单）：缩放、重新布局、显示网格、输出到图形文件。

**类属性分组显示**：选中类的"属性"标题 → 右键 → "分组属性"

### 2.8 描述属性的查看与编辑

`【手册】`

UBF Studio 中各级元素多数具有**描述属性**（不同于类属性只存在于类中）。

**三种查看方式**：

1. **属性页**（公共管理工具）：显示及修改当前选定对象的描述属性。有两种排序方式——按类别分组显示 / 打破类别按名称顺序排列
2. **浮动属性编辑器**：双击模型元素即可打开。下部无标题空白文本框是**备注项**，可录入伪代码等信息
   > **小技巧**：备注项文本框太小时，**双击该文本框**可在放大的文本框中编辑
3. **详细信息窗格**：打开模型后，在输出查看器所在窗格会新增"详细信息"页签。根据模型种类不同，会分为多个子页签（类属性、方法、版型、实现策略等）

**详细信息窗格快捷操作**：

| 快捷键 | 功能 |
|---|---|
| `Arrow` | 移动到上/下一行或上/下一列 |
| `Ctrl + Arrow` | 移动到第一行/最后一行或第一列/最后一列 |
| `Ctrl + C / X / V` | 单元格中复制、剪切、粘贴 |
| `F4` | 可参照输入的描述属性弹出参照选择框（如数据类型、校验器）；下拉列表输入的打开下拉框 |
| `Delete` | 删除一行 |
| 在最后一行的名称列输入值 | **自动添加**一个属性/方法/参数 |

> **小技巧**：对"服务可见"、"可空"、"是否隐藏列"等复选框输入的列，可以**批量设置全选/全部取消**——方法是**选择顶部空白行的复选框**。

**模型元素共有的描述属性**：

| 标签 | 含义 | 输入说明 |
|---|---|---|
| 名称 | 唯一性名称，在生成的源码中使用 | 以字母开头的英文 |
| 全名 | 全路径名称 | 系统自动生成，不可修改 |
| 显示名称 | 多语种显示名称，可更换语种 | 目前建议直接输入中文。需要其它语种时可直接在资源中维护 |
| 描述 | 描述性解释 | 直接输入或参照资源输入 |
| 备注 | 用于输入备注文本信息，常用来输入伪代码 | 直接输入，文本较多时可双击窗口放大编辑 |
| 隐藏显示 | 当前类属性是否需要在模型图中隐藏显示，**只用于类属性** | 复选框 |

> **重要缺省规则**：`描述` 和 `显示名称` **只在 UBF 中有效，不出现在构造生成文件中**。`名称` 在实体实例中必须唯一，且**只能以字母开头，只能包括字母和数字**。

## 3. 实体模型开发（BE）

### 3.1 开发流程总览

`【手册】`

建立业务模型是应用开发过程的**第一步**。可开发的模型有：实体模型、业务操作模型、服务模型、数据库模型。

**实体项目的创建过程**：

1. 建立**组件**、文件夹（可选）和**命名空间**
2. 在命名空间下建立**实体、枚举、属性类型、校验器、数据传输对象**等模型元素
   > 可以首先建立**类图**以方便各模型的快速创建与可视化编辑。**特别地，各模型间的关系只有通过类图才可创建与编辑。**
3. 实体项目的**发布有三条线同时进行**：
   - i. 生成代码 → 修改代码 → 编译发布为运行期组件
   - ii. 实体项目的 **DSL 文件直接发布到运行期元数据库**中
   - iii. 由实体项目创建**数据库项目**

**数据库项目**：

1. 可以由实体项目**自动创建**（创建时同时生成**数据表和 OR 映射文件**）；也可以手工创建数据表并手工建立表与实体对象之间的 OR 映射关系
2. **OR 映射文件**直接发布为运行期的 OR 映射文件
3. 数据库项目中的表**只是存在本地的描述文件**，需要据此**生成建库脚本**，并针对指定的数据库服务器**执行建库脚本**，才生成真正的数据表供运行期程序使用

> **划重点**：这三条线说明了"元数据 → 代码 / 元数据库 / 物理表"的完整生成链路。**物理表是通过执行建库脚本生成的，不是手写的。**

### 3.2 新建实体项目

`【手册】`

**操作步骤**：

1. IDE 中"文件" → "新建" → "新建解决方案"；或在解决方案视图中选中解决方案节点，选择右键菜单"新建"
2. 在新建解决方案对话框中**勾选实体项目类型**
3. 输入解决方案名称
4. 选择解决方案文件路径
5. "确定"

**缺省规则**：

1. 勾选实体项目后会默认创建相应的实体项目文件
2. **解决方案名称只能以字母开头，且只能包括字母和数字**
3. 每个解决方案对应生成一个解决方案文件，扩展名 `.ubfsln`

5. 每个实体项目对应生成一个项目文件 `.ubfmlproj`；每个实体组件对应生成一个实体组件文件 `.ubfbe`

**几个关键属性的实际含义**：

| 属性 | 为什么重要 |
|---|---|
| `可扩展` | 决定该属性是否允许客开扩展 |
| `一旦使用不可修改` | 防止已投产字段被改类型/长度，**保护线上数据** |
| `计算列` + `表达式` | 公式计算字段，**不落物理表**，界面可见 |

> **与 DTO 清单的关联**：DTO 里看到的字段，就是那些 `服务可见 = True` 的属性在 API 层的投影。反过来，**`服务可见 = False` 的属性不会出现在 DTO 里**——这是 DTO 清单无法覆盖全量字段的根本原因（见 `references/api-dto.md`）。

**其他模型元素的属性设计**（属性项与实体属性大同小异，此处只列差异）：

| 模型 | 特有属性项 |
|---|---|
| 数据传输对象（DTO） | `是否查询DTO`；属性无"关联实体是否可见"，但同样有 `计算列`/`表达式`/`长度`/`可空`/`只读`/`同步字典` |
| 属性类型（Property Type） | 属性有 `查询属性`、`关联实体是否可见` |
| 枚举类型 | 类型级 `可扩展`；属性级有 `系统值`（选择框） |
| 校验器 | 属性有 `长度`、`最大值`、`最小值`、`同步字典` |
| 视图 | 类型级有 `过滤条件`（弹出"表达式"窗口）、`数据库视图名称`；属性级有 `栏目待选`、`默认栏目`、`排序待选`、`条件待选`、`是否输出`、`排序类型`、`排序顺序`、`输出` |

| 事件 | 与实体基本一致 |

### 3.10 模型元素的复用机制

`【手册】` 这是 UBF 降低重复开发的核心能力，三种机制：

#### 3.10.1 模式（Pattern）

**应用模式**：

1. 在类图中单击鼠标**右键**，在弹出菜单中选择"应用模式"
2. 在弹出对话框中选择要应用的模式，点击确认
3. 弹出**模式参数对话框**，列出当前模式里所有的类：
   - 可以从当前组件中选择一个**已有的类替换**模式中的类
   - 也可以不替换，系统会**创建一个新类**
4. 点击确定，系统自动在当前组件中创建该模式所有需要的类以及类之间的关系
   - 如果选择用已有的类替换，则系统会将模式中被替换类中的**属性和关系复制到替换类**中
5. 在标题文本框中可以修改将要创建的类的名称

**其他操作**：生成模式、创建模式项目。

#### 3.10.2 版型（Stereotype）

- 版型是**扩展业务实体描述**的一种解决方法
- 主要用于表现一些**不在模型上体现的业务规则**，**主要用于扩展代码**
- 相关操作：应用版型、版型设置、版型模板（**TPL 文件**）

#### 3.10.3 特性（Feature）

- 特性是**被抽象出来并可在实体设计时被复用的、代表特定方面（Aspect）特征的属性集**
- 相关操作：应用特性、生成特性、创建特性项目

## 4. 服务模型开发（SV / BP）

### 4.1 操作项目 vs 服务项目

`【手册】`

- 业务模型可开发的模型有：实体模型、**业务操作模型**、**服务模型**、数据库模型
- 对应项目：实体项目、**业务操作项目**、**服务项目**、数据库项目

## 5. 界面模型与表单开发（UI）

### 5.1 界面设计词汇表

`【手册】`

| 中文 | 英文 | 解释 |
|---|---|---|
| 界面模型 | UI Model | 实际界面和后台逻辑之间的**抽象层**，用于在不同类型的客户端显示相同的界面逻辑 |
| 界面视图 | UI View | 是界面模型的某种视角的**扁平化**表现形式 |
| 界面连接 | UI Link | 界面主子视图之间的关联关系 |
| 界面字段 | UI Field | 界面视图中的数据项。对于实体绑定视图，**对应于实体中的类属性** |
| 界面辅助属性 | UI Auxiliary Property | 分两类：**界面模型辅助属性**（从属于界面模型的单值变量）、**界面视图辅助属性**（从属于单个界面视图的单值变量，可跟随所属视图存在于相同的表单容器中） |
| 界面记录 | UI Record | 界面视图的数据行 |
| 界面过滤器 | UI Filter | 界面视图的数据行过滤条件 |
| 界面动作 | UI Action | 响应用户界面操作的前端逻辑 |
| 动作特性 | Action Feature | 界面动作的一种共享与复用方式。将一组界面动作保存后，可复用于其它界面模型 |

### 5.2 UI Model 的内容构成

`【手册】`

**视图（UI View）** —— 界面显示数据的主体

- 可以来自领域模型的实体（**实体绑定视图**）
- 也可以在界面项目中自行创建（**实体无关视图**）
- 视图由以下部分组成：
  - **界面字段（UI Field）**：界面中显示的数据项，在具体界面中表现为**数据绑定控件**。类似于实体类属性，**可以进行分组管理**
  - **默认的过滤器**：在当前视图中，只显示符合条件的界面记录
  - **属性组**：视图内的界面辅助属性集合，用于显示"一个视图只有一个取值"的界面数据项

**连接组** —— 用于描述各个视图之间的关系

- 对于实体绑定视图，**界面连接对应于实体间的关系**

**属性组** —— 视图之外从属于整个界面模型的界面辅助属性集合，用于显示"一个界面模型只有一个取值"的界面数据项

**动作组** —— 用于保存用户界面事件发生后的界面执行逻辑

- 除通用的 CRUD 操作之外，开发人员可以定义新的动作及界面执行逻辑
- 动作组中的动作**可以分组管理**

> **设计目标**：界面模型的设计目标在于为不同类型的客户端表示层提供**一致的前端业务逻辑的模型和控制**，充当 **MVC 框架中的模型和控制器**角色。常见客户端包括网页浏览器、Windows 界面、手机终端、掌上电脑等。

## 6. 扩展字段：客开的核心场景

> 这是"在现有表单上扩展字段"的标准答案章节。

### 6.1 三条路径对比

`【官方】` `【社区】`

| 路径 | 做法 | 代价 | 升级安全 |
|---|---|---|---|
| **A. 弹性域预置字段** ⭐推荐 | 直接占用产品单据预置的 **50 个公共字段** / **30 个私有字段** | **最低，不动元数据** | ✅ 安全 |
| **B. 扩展实体 + 元数据绑定** | 用 U9 Studio 元数据编辑器新建**扩展实体**，在扩展实体上增加自定义字段 | 中等，需发布元数据 | ✅ 安全 |
| **C. 直接改物理表** | 在 SQL Server 标准表上加列 | — | ❌ **严禁**，升级会被覆盖 |

> **结论**：**如果只是加几个业务字段，优先走 A。**

### 6.2 路径 A：弹性域预置字段

`【官方】`

- 产品单据**预置了 50 个公共字段和 30 个私有字段**，专门用于单据扩展
- **公共字段可自动实现单据上下游传递**——这是公共字段相对私有字段的核心优势
- 在表单设计器中使用**弹性域控件**（见 [5.10](#510-弹性域控件)）来呈现

> **对数仓的影响**：弹性域字段在 API/DTO 层统一表现为 `DescFlexFieldRData`（含 80 个字段），**从 DTO 层看不出里面实际装了什么**。如果字段清单需要知道弹性域里装了什么，必须去查元数据或问业务方。

### 6.3 路径 B：扩展实体

`【社区】`

**做法**：

1. 用 U9 Studio 的**元数据编辑器**新建一个**扩展实体**
2. 在扩展实体上增加**自定义字段**
3. U9 运行时会**自动将扩展字段加载进标准实体实例**，**界面表现和标准字段基本无差别**

**扩展表命名**：默认带 `_EXT` 后缀，或按扩展包命名（`【待核实】`，见表前缀警告）。

### 6.4 关键属性（决定字段能否被下游携带）

`【社区】`

这几个属性决定了扩展字段**在下游服务中是否能被正常携带**：

| 属性 | 含义 | 影响 |
|---|---|---|
| **Reference** | 引用属性 | 字段是否引用其它实体 |
| **OrgScope** | 组织隔离 | 字段是否按组织隔离取值 |
| **ValueChange** | 值更新规则 | 字段值变化时的处理规则 |
| **TransferFlag** | **允许传递** | ⭐ **决定字段能否随单据进入下游对象** |

> **实战案例**：给采购订单新增一个"内部备注"字段，**如果希望它随单据一起进审批流对象，就必须设置"允许传递"属性**，否则**审批表单里永远看不到这个字段的值**。

**元数据 XML 示意**（`【待核实】` 格式示意，非官方 schema）：

```xml
<Field Name="InternalMemo" DisplayName="内部备注" DataType="String"
       Length="500" AllowNull="true" OrgScope="Organization"
       TransferFlag="true" />
```

### 6.5 风险与约束

| 风险 | 说明 | 应对 |
|---|---|---|
| 直接改标准表 | 升级时冲突/被覆盖 | 走 A 或 B |
| 忘记设 `TransferFlag` | 字段在下游/审批流中不可见 | 扩展时明确字段的流转需求 |
| 弹性域字段语义丢失 | 从 DTO/API 层看不出弹性域装了什么 | 维护弹性域字段台账，记录每个预置字段的业务含义 |
| 元数据发布冲突 | 多人同时改元数据 | 走源代码版本管理（见 [2.6](#26-源代码版本管理)） |
| 历史数据未回填 | 新增字段后老单据无值 | 评估是否需要回填脚本 |

## 7. 数据访问：OQL 与三个查询类 ⭐

`【官方】` 摘自《U9研发体系（实体操作API参考手册）》

> **这是读数据的第一选择**，优先级高于 `DataAccessor.RunSQL`。OQL 走实体层，**会自动套用实体的业务规则、权限与多语**，且天然参数化。
>
> 写实体模型 / 服务模型的业务代码时用本章。**插件（BE/BP/UI）本身的开发流程、调试**见 `references/plugin-dev.md`。

### 7.1 三个查询类的分工

| 类 | 命名空间 | 返回 | 用于 |
|---|---|---|---|
| **`EntityDataQuery`** | `UFSoft.UBF.Business` | `IDataReader` / `DataSet` / 单值 | 只要数据不要行为：报表、导出、接口。**最常用** |
| **`EntityQuery`** | `UFSoft.UBF.Business` | 实体 / 实体集合 | 需要拿到实体对象继续操作（改值、保存） |
| **`EntityViewQuery`** | `UFSoft.UBF.Business` | 视图对象 | 对**视图/临时表**操作，复杂查询。**需自己处理数据库连接** |

### 7.2 OQL 语法要点

- **实体引用用 `::` 分隔命名空间**：`Association::Yel_Ass1to1_A`
- 完整 OQL：`select ID,Name,Code from Association::Yel_Ass1to1_A where ID > @ID order by ID`
- 也可以**只写条件部分**：`ID > @ID and Name = @mmm order by ID`
- 支持子查询：`... where ID not in (select ID from Association::Yel_Ass1to1_B)`
- 支持聚合单值：`select Max(ID) where id > 111`、`select sum(ID) where id > 111`
- **`select *` 是坑**：`*` 的解析**依赖表结构而不是实体结构**。返回实体集合时**必须显式列出全部属性名**：
  `select ID,Name,Code,CreatedOn,CreatedBy,ModifiedOn,ModifiedBy,SysVersion from ...`

### 7.3 `EntityDataQuery` 方法速查

| 方法 | 说明 |
|---|---|
| `Select(...)` | 指定查询字段（**显式列，别用 `*`**） |
| `Parameters.Add(new OqlParam(x))` | 加查询参数 |
| `FindDataSet()` / `FindDataSet(condition)` | 查全部 / 按条件查，返回 `DataSet` |
| `FindDataSetByPage(pageIndex, pageSize, oql)` | 分页查 `DataSet` |
| `FindDataReaderByPage(pageIndex, pageSize, oql)` | 分页查 `IDataReader` |
| `FindValue()` / `FindValue(condition)` | 无条件 / 带条件单值查询（第一行第一列） |
| `IsExists(oql)` | 判断是否存在符合条件的记录 |

**创建方式**：

```csharp
// 方式 1：直接给实体名
UFSoft.UBF.Business.EntityDataQuery q = new UFSoft.UBF.Business.EntityDataQuery("Association.Yel_Ass1to1_A");

// 方式 2：从实体的 Finder 拿
EntityDataQuery q1 = Yel_Ass1to1_A.Finder.CreateDataQuery();
```

### 7.4 参数绑定的两种方式 ⚠️

| 方式 | 写法 | 约束 |
|---|---|---|
| **按顺序绑定** | OQL 里用 `@p1`、`@p2` | 参数个数**必须**与 OQL 中占位符个数一致 |
| **按名称绑定** | OQL 里用 `@Name` | 参数名**必须**与 OQL 中占位符名一致 |

```csharp
query.Select("ID", "Code", "Yel_Ass1to1_B.Name", "Yel_OtherAss_A.ModifiedOn");
query.Parameters.Add(new OqlParam(1));                              // @ID
query.Parameters.Add(new OqlParam("TestFindByPageUsingDataReader")); // @mmm
IDataReader dr = query.FindDataReaderByPage(0, 2, " ID > @ID and Name = @mmm order by ID");
```

### 7.5 分页的特殊取值 ⚠️

`pageIndex` 与 `pageSize` 有**约定俗成的特殊值**，官方手册的表述是：

| 参数 | 特殊值 | 含义 |
|---|---|---|
| `pageIndex` | **-1** | 取**最后一页** |
| `pageSize` | **-1** | 取**全部数据** |

```csharp
query.FindDataReaderByPage(0, 2, cond);    // 第 1 页（索引从 0 起），每页 2 条
query.FindDataReaderByPage(1, 2, cond);    // 第 2 页
query.FindDataReaderByPage(-1, 3, cond);   // 最后一页，每页 3 条
query.FindDataReaderByPage(2, -1, cond);   // 从第 3 页起取全部
```

> **`IDataReader` 用完必须 `Close()`**，否则连接不释放。

### 7.6 `EntityQuery` 的缓存行为

- `Finder.FindByID(id)` — **先从缓存取，缓存没有再查库**
- `Finder.FindAll(oql, params)` — **直接从数据库取**（不走缓存）
- `Finder.Find(condition)` — 按条件查

> **含义**：同一个 Session 内 `FindByID` 可能拿到缓存对象。**要读数据库最新值，用 `FindAll` 或 `EntityDataQuery`。**

## 8. 事务与 Session

`【实测】`（工匠智造文档，轻量服务项目实操）

### 8.1 大事务：`UBFTransactionScope`

跨多个实体操作、需要显式控制提交/回滚时用：

```csharp
using (UBFTransactionScope scope = new UBFTransactionScope(TransactionOption.RequiresNew))
{
    // ... 业务操作

    scope.Rollback();   // 回滚
    // 或
    scope.Commit();     // 提交
}
```

### 8.2 小事务：`Session.Open()`

单实体改值保存时用：

```csharp
using (Session session = Session.Open())
{
    RcvRptDoc rcvRptDoc = RcvRptDoc.Finder.FindByID(createResult.ID);
    rcvRptDoc.RcvDep = "xxx";
    session.Commit();
}
```

### 8.3 实体操作的三条红线

`【官方】` 摘自《U9研发体系（实体操作API参考手册）》

1. **删除实体只能用 `Remove()` 方法**。对一对多子对象用集合的 `Clear()` **不会删除**——`Clear()` 只是集合自身的方法，不是持久层的删除。
2. **删主实体会自动删除从实体**（1:1 / 1:N 都成立）。
3. **`session.Modify(obj)` 是特殊做法，官方明确不推荐**（遇到需要外部传入实体的场景才用）。

### 8.4 上下文获取

```csharp
PlatformContext context = PlatformContext.Current;
```

> **与插件事务的关系**：BE 插件默认运行在业务操作的同一个数据库事务内（插件抛异常 → 整个业务操作回滚），见 `references/plugin-dev.md` 第 3 章。

## 9. 命名规范与开发约定

`【手册】` 通用缺省规则：

| 项 | 规则 |
|---|---|
| **名称** | 只能以**字母开头**，且只能包括**字母和数字**；在实体实例中必须**唯一** |
| 解决方案名称 | 只能以字母开头，且只能包括字母和数字 |
| UI 界面项目名称 | 只能以字母开头，且只能包括字母、数字、下划线、圆点符号 |
| **描述** | 只在 UBF 中有效，**不出现在构造生成文件中** |
| **显示名称** | 只在 UBF 中有效，**不出现在构造生成文件中** |
| 显示名称语言 | 建议直接输入中文；需要其它语种时在资源中维护 |

`【社区】` 提到的命名约定范围：配件名、**BE 表名**、科目名称等（具体规范需查官方客开培训资料）。

> **官方手册参考**：iufida 资料站的《用友U9客户化开发实战》课程讲义中，命名规范涵盖"配件名、BE 表名、科目名称"等约定，并给出了**组件、类实体、属性及 UIForm/Part/Page 的元数据关系查询 SQL**，以及**同步枚举脚本**的处理逻辑。这是查找元数据关系的高效工具，值得获取。

## 10. 开发类问题排查

`【社区】`

| 现象 | 排查方向 |
|---|---|
| 扩展字段在审批流中不可见 | 检查 `TransferFlag`（允许传递）是否设置 |
| 字段在列表/查询中查不到 | 检查实体的 `查询属性` 是否为 `True`——**只有具有业务含义的类属性才能用于智能查询（SmartList）** |
| 界面字段与实体字段对不上 | 检查 UIModel 与 Form 的绑定关系（见 [5.7](#57-表单form开发)） |
| 改完元数据运行期不生效 | 检查 DSL 文件是否已发布到运行期元数据库 |
| 元数据发布后标准功能报错 | 检查是否与标准元数据冲突；检查升级补丁 |
| 站点起不来 | 检查 IIS 与 SSRS 配置 |
