# 主题② 接口 / DTO / 字段查询

> 覆盖：U9C 官方 OpenAPI 的 DTO 层、本项目字段清单的用法、枚举与弹性域、**物理表名的获取途径**、DTO 的能力边界。
> 典型问法："采购订单有哪些字段"、"这个字段什么意思"、"单据状态枚举值"、"物理表名是什么"。

---

## 1. 三层链路（理解 DTO 的关键）

```
物理表（SQL Server）  ←──UBF OR 映射──→  业务实体 BO（元数据）  ──序列化──→  DTO（API 投影）
      ↑                                        ↑                              ↑
  真实存储                                  元数据库定义                    OpenAPI spec
  表名/列名/索引                          字段/校验/默认值                 服务可见字段
```

- **DTO 是元数据的下游产物**，不能反过来当作元数据定义使用
- DTO 只包含 `服务可见 = True` 的属性，**不是全量字段**
- DTO 用业务编码（Code）而非物理 ID 做维度引用

### 1.1 DTO 是什么（比喻）

把 U9 想成一家餐厅：

- **物理表** = 后厨的货架和冰箱。东西真放在这里，但外人进不去，标签也乱（列名无业务含义）
- **业务实体 BO** = 后厨的菜谱。定义了每道菜要哪些料、怎么校验、默认放多少
- **DTO** = 递给客人的**点菜单**。只列客人能点的菜，用客人看得懂的名字，**不暴露后厨长什么样**

所以：**DTO 能告诉你"有什么菜、叫什么名"，但告诉不了你"菜放在哪个货架第几层"。**

| 查哪些实体引用了某维度 | Grep 「关联实体」列 |

## 4. 枚举与特殊字段

### 4.1 枚举的两种描述形态

「枚举值」列由 `extract_u9c_fields.py` 的 `parse_enums()` 解析，官方 spec 里存在两种形态，产出两种格式：

| 形态 | 源描述示例 | 产出格式 | 说明 |
|---|---|---|---|
| **多行制表符表**（值在行尾） | `Opening\t开立\t0` | `Opening=开立(0)` | 同时含英文名与中文名，**信息最全** |
| **单行内联**（值在前） | `单据状态：0开立；1审核中；2已审核` | `开立(0); 审核中(1); 已审核(2)` | 只有中文名，无英文标识符 |

单行内联还含若干子型，均已支持：`0：客户`（冒号）、`1-收入`（连字符）、`0,待检`（逗号）、`2.删除`（点号）、`0 新增`（空格）、`0新增`（无分隔符），以及名称在前的 `开立 Value:0`。

> **历史缺陷已修复**（2026-09-24）。修复前解析器只认多行制表符表，全量 11,968 个字段中仅 14 个抽到枚举值；修复后为 **161 个**。`DocStatus` 是受影响最广的字段（23 个实体）。
>
> 同日的第二轮修复清除 2 处**过抽**：`VoucherRData` 的英文备注 `add by leixyu 20230109` 被形态 1 拆成 `name=add / label=leixyu / value=20230109`，误产出 `add=leixyu(20230109)`。现要求形态 1 的标签必须含中文（`RE_CJK`），163 → 161。

**已确认的单据状态口径**（可安全使用）：

| 值 | 含义 |
|---:|---|
| 0 | 开立 |
| 1 | 审核中 |
| 2 | 已审核 |
| 3 | 关闭（仅部分单据有此值） |

> **解析器刻意保守**：单行描述正文里同样会出现「数字+汉字」（如"若ID&gt;0优先按ID取"），因此要求命中项 ≥2 且相邻项之间只隔分隔符才认定为枚举；多行制表符表则要求标签含中文。**代价是少数非标准写法抽不到**（如 `PM005 标准采购 316` 这类"名称 中文名 值"三列文本、`One 0` 两列文本），此时枚举值仍混在「中文含义」列，需人工判读。

### 4.2 弹性域 `DescFlexFieldRData` ⚠️

产品单据预置 **50 个公共字段 + 30 个私有字段**用于扩展（见 `references/ubf-uap-dev.md`）。

在 DTO 层，这些字段**统一表现为 `DescFlexFieldRData`**，从 DTO 看不出里面实际装了什么。

> **结论**：字段清单无法回答"弹性域里装了什么"。要拿这个语义，必须查元数据或问业务方。维护**弹性域字段台账**是唯一办法。

### 4.3 `IDCodeNameDTOData` —— 维度引用三件套

U9 的维度引用对象同时携带 **ID + Code + Name**：

| 字段 | 说明 |
|---|---|
| `ID` | 物理主键 |
| `Code` | 业务编码 |
| `Name` | 名称 |

> 这一点由 BP 插件调用 ISV 代理的实测代码印证：`dtoData.ID = Convert.ToInt64(dataRow["PRID"]);`（见 `references/plugin-dev.md` 第 4 章）。

## 5. 元数据属性 → DTO 的映射

实体属性上的这几个属性决定了它在 DTO 里长什么样：

| 元数据属性 | 对 DTO 的影响 |
|---|---|
| **`服务可见`** | ⭐ **决定该属性是否出现在对外服务/DTO 中**。这是 DTO 字段清单的源头 |
| `可扩展` | 决定该属性是否允许客开扩展 |
| `计算列` + `表达式` | 公式计算字段，**不落物理表**，但界面可见 |
| `一旦使用不可修改` | 防止已投产字段被改类型/长度，保护线上数据 |
| `业务主键` | 参与业务唯一性判定 |
| `同步字典` | 与字典表同步 |
| `是否敏感日志字段` | 日志脱敏控制 |
| `查询属性` | **只有具有业务含义的类属性才能用于智能查询（SmartList）** |

> **反向推论**：`服务可见 = False` 的属性不会出现在 DTO 里——**这是字段清单无法覆盖全量字段的根本原因**。

## 6. ⭐ 物理表名的获取途径

> ⚠️ **先读硬护栏**：公网上 U9 物理表前缀有两套互相矛盾的说法（`CBO_`/`SM_`/`PM_`/`InvTrans_` vs `T_BAS_`/`T_SO_`），**均未经权威验证，不要采信任何一套**。

**途径 1：查 U9 元数据库**（唯一可靠）

元数据库（Metabase）存有实体定义、OR 映射、缺省表名。这是权威源。

**途径 2：用 BE 实体查询当数据字典**（`【社区】`，最实用）

用 BE 实体建立报表时可以直接查询实体字段。实际做报表时这个功能用得少，但**用来当数据字典非常高效**：

- **A.** U9 数据库更新频繁，但**数据字典不能及时更新**，有时会出现数据字典中找不到字段的情况
- **B.** BE 实体**查字段速度快且效果直观**
- **C.** 只有需要知道字段意义时才需要翻数据字典，而这个方法可以省略

操作：新建报表容器 → 报表 → 连接数据源（server name 直接输 IP）→ 增加数据查询 → **提供者类型选 `BusinessEntity`** → 选择实体（用"查找实体"更快）→ 选字段 → 保存 → 可预览数据 → 可用 UBF 自带工具**翻译成 SQL**。

**途径 3：用 F12 抓字段名**（`【社区】`）

用浏览器打开 U9 单据页面，**F12 开发者工具就能捕捉到对应的字段名称**。**前台字段名称与后台字段名称是相同的。**

**途径 4：查数据库项目的"缺省表名"**

实体属性里有 `缺省表名`（默认取实体名称）。**但实际物理表名可能被 OR 映射覆盖，必须通过数据库项目确认最终表名。**

> **途径 2 + 3 的组合价值**：这是绕开"拿不到物理表 DDL"困境的**实用替代方案**——通过 BE 实体查询 + F12 反查，可以定位到具体字段及其业务含义，无需等待数据字典。

## 7. DTO 的能力边界

| 能力 | DTO 清单 | 说明 |
|---|:---:|---|
| 字段名 + 类型 | ✅ | |
| 字段中文含义 | ✅ | 覆盖率 50%~92%，视域而定 |
| 字段引用哪个实体 | ✅ | |
| 必填 / 默认值 | ✅ | 部分 |
| **物理表名 / 列名** | ❌ | 需走元数据库或 BE 实体查询 |
| **索引 / 校验规则** | ❌ | 定义在实体元数据中 |
| **`服务可见 = False` 的字段** | ❌ | 元数据里可见，DTO 里没有 |
| **弹性域内容** | ❌ | 统一表现为 `DescFlexFieldRData` |
| **枚举值** | ⚠️ | 已结构化 161 个字段；少数非标准写法（"名称 中文名 值"三列等）仍需人工判读，见 4.1 |

### 7.1 接口调用能力评估

| 用途 | 可行性 |
|---|---|
| 接口对接、字段映射 | ✅ 直接可用 |
| 识别幂等键（业务主键） | ✅ |
| 枚举 → 字典表转换 | ⚠️ 需先修复枚举解析 |
| 维度建模输入（DIM/DWD 设计） | ✅ 部分（缺物理表名） |
| 直接查数据库 | ❌ DTO 不是物理 schema |
| UAP Studio 新增表单 / 扩展字段 | ❌ **方向反了**——DTO 是元数据的下游，不是设计入口。走 `references/ubf-uap-dev.md` |
